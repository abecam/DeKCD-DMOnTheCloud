Knowledge graphs

1 Scope

While setting up a Data Management Platform, you will have to choose a compatible way to store the data, which will be documented in the Data Management Platform’s documentation. In this case, you generally do not have to care about the implementation, even if it could help for certain cases and for maintenance.

But Knowledge graphs answer a more general need: they are a way to represent data with semantic meaning, with shared, agreed-upon vocabularies and ontologies. As such, they are a good way to help with the Interoperability and Reusability of data, the IR of FAIR.

Another interesting aspect is how they can be queried and navigated, which is a good way to help with the Accessibility of data, the A of FAIR. SPARQL is a standard query language for most knowledge graphs (those based on RDF), and it is possible to use a LLM to query a SPARQL endpoint or create queries.

Knowledge graphs are therefore not necessarily a replacement for existing storage solutions, but rather a way to describe, connect, and query data across systems, potentially complementing relational databases and other storage technologies.

2 What are Knowledge graphs

Knowledge graphs represent data in a graph structure where nodes represent entities and edges represent relationships between those entities.

2.1 Definition

A knowledge graph is a way of organizing information as a network of entities (people, places, concepts, datasets) connected by labeled relationships, typically stored as subject-predicate-object triples like “Marie Curie-> won -> Nobel Prize in Physics.” Because the data is structured as nodes and edges, often with a shared schema or ontology that defines what types of things and relationships exist, it can be queried, linked across sources, and reasoned over to reveal connections that would be hard to see in flat tables or unstructured text. Knowledge graphs power things like search engine info panels, recommendation systems, and data integration across research or enterprise systems.

2.2 Current solutions

2.2.1 RDF

One prevalent method to store a knowledge graph is RDF, Resource Description Framework. It is not a language, but a list of definitions (framework) that can be “implemented” using various serialization formats: i.e. how it is stored in a file.

The first serialization format was RDF/XML. It is not very readable and difficult to write, but might be used in many legacy systems and graphs. If you need to write a knowledge graph in this format, it might be a better approach to use either Turtle or JSON-LD (see below) and use a conversion tool to RDF/XML.

<rdf:RDF xmlns:rdf="http://www.w3.org/1999/02/22-rdf-syntax-ns#"
         xmlns:ex="http://example.org/">
  <rdf:Description rdf:about="http://example.org/MarieCurie">
    <ex:won rdf:resource="http://example.org/NobelPrizePhysics"/>
  </rdf:Description>
</rdf:RDF>

The 2 most popular formats now are Turtle (.ttl) and JSON-LD (.jsonld).

Turtle is the most human readable and the easiest to write by hand.

@prefix ex: <http://example.org/> .

ex:MarieCurie ex:won ex:NobelPrizePhysics ;
              ex:bornIn ex:Warsaw .

JSON-LD is also quite simple and used for embedding structured data in HTML pages (schema.org markup) and for APIs

{
  "@context": { "ex": "http://example.org/" },
  "@id": "ex:MarieCurie",
  "ex:won": { "@id": "ex:NobelPrizePhysics" },
  "ex:bornIn": { "@id": "ex:Warsaw" }
}

Embedded in HTML, using schema.org vocabulary:

<script type="application/ld+json">
{
  "@context": "https://schema.org",
  "@type": "Person",
  "name": "Marie Curie",
  "birthPlace": "Warsaw"
}
</script>

Other formats are:

  • N-Triples (.nt), a line-based format with one full triple per line and no prefixes. It’s easy to parse and stream, so it’s often used for large dumps and data exchange.
  • N-Quads (.nq) extends N-Triples with a fourth element for the named graph, and TriG (.trig) does the same for Turtle. Both are used when you need to store multiple graphs in one file.

3 What to use when: Knowledge graphs, Relational Databases, NoSQL Databases

Relational databases offer a clear benefit for storing repeated data with clear relationships between them, with fast and relatively simple queries.

But if the data starts to self-reference, queries become more complex and less efficient. Database normalisation avoids such problems, but it is not always possible or desirable to normalise the data. In such cases, it can be better to opt for a NoSQL database or a knowledge graph, which are more flexible.

Note that a NoSQL database can be stored in a relational database, and a knowledge graph can be stored in a NoSQL database, and by extension in a relational database (which might be poorly suited for navigating a knowledge graph).

A NoSQL database is an technical solution to store data in a flexible way, with no predefined assumptions other than the basic structure: a set of key-value pairs, key-columns, graph, … A knowledge graph is a higher level solution to represent data with semantic meaning, with a predefined structure: a set of triples (subject, predicate, object).

As such, it is simpler to consider the benefits of a knowledge graph first: it offers a known, standardised, and widely used structure to represent data with semantic meaning with their relationships, and it is easier to query and navigate the data (with a standard query language such as SparQL).

There exists several kinds of NoSQL databases:

  • Key-value stores: store data as a collection of key-value pairs, where each key is unique and maps to a specific value. Examples include Redis and Amazon DynamoDB.
  • Document stores: store data as documents, typically in JSON or BSON format, where each document can have a different structure. Examples include MongoDB and Couchbase.
  • Column-family stores: store data in columns rather than rows, allowing for efficient storage and retrieval
  • Graph databases: store data as nodes and edges, allowing for efficient representation of complex relationships. Examples include Neo4j and Amazon Neptune.
  • Multi-model databases: support multiple data models, allowing for flexibility in how data is stored and queried. Examples include ArangoDB and OrientDB.

Each kind of NoSQL database has its own strengths and weaknesses, and the choice of which one to use will depend on the specific requirements of the application.

3.0.1 OWL

RDF only says that two things are related, not what the relationship or the types mean. OWL (Web Ontology Language) adds this meaning. It is a vocabulary built on top of RDF (and RDFS) for describing classes, properties and the constraints between them, so it is not an alternative to RDF but an extension of it. An OWL ontology is itself stored as RDF, typically in Turtle or RDF/XML.

With OWL you can, for example, declare that:

  • Scientist is a subclass of Person
  • won links a Person to a Prize
  • bornIn can have only one value per person
  • spouseOf is symmetric
@prefix ex:   <http://example.org/> .
@prefix owl:  <http://www.w3.org/2002/07/owl#> .
@prefix rdfs: <http://www.w3.org/2000/01/rdf-schema#> .

ex:Person    a owl:Class .
ex:Scientist a owl:Class ;
             rdfs:subClassOf ex:Person .
ex:Prize     a owl:Class .

ex:won a owl:ObjectProperty ;
       rdfs:domain ex:Person ;
       rdfs:range  ex:Prize .

ex:bornIn a owl:ObjectProperty , owl:FunctionalProperty .

ex:spouseOf a owl:ObjectProperty , owl:SymmetricProperty .

ex:MarieCurie a ex:Scientist ;
              ex:spouseOf ex:PierreCurie .

A reasoner (e.g. HermiT, Pellet, or the one built into Protégé) can then infer facts that were never written down: Marie Curie is a Person (because every Scientist is), and Pierre Curie is the spouse of Marie Curie (because spouseOf is symmetric). It can also flag contradictions, such as a person with two different birthplaces.

OWL ontologies are usually edited with Protégé. For validating the shape of data rather than inferring new facts, SHACL is often used alongside OWL. SHACL (Shapes Constraint Language) is a standard language for describing RDF graphs.

3.0.2 Other solutions

3.0.2.1 Labeled Property Graphs (LPG)

In a labeled property graph, nodes and edges can both carry a label and arbitrary key-value properties. This is the model used by most graph databases, such as Neo4j, Amazon Neptune (which supports both models), Memgraph or JanusGraph. Compared with RDF, it is more compact when you want to attach details to a relationship (e.g. the year of the prize), because edges can have properties directly. The trade-off is that there is no global standard for identifiers and vocabularies, so sharing and merging graphs across organisations is harder.

The same facts in Cypher (Neo4j’s query language, which is also the basis of the ISO standard GQL):

CREATE (curie:Person {name: "Marie Curie"})
CREATE (nobel:Prize {name: "Nobel Prize in Physics"})
CREATE (warsaw:City {name: "Warsaw"})
CREATE (curie)-[:WON {year: 1903}]->(nobel)
CREATE (curie)-[:BORN_IN]->(warsaw)

Querying it:

MATCH (p:Person)-[w:WON]->(prize:Prize)
RETURN p.name, prize.name, w.year

Other query languages for property graphs are Gremlin (Apache TinkerPop) and, more recently, GQL (ISO/IEC 39075:2024).

3.0.2.2 RDF-star (RDF 1.2)

To get the best of both worlds, RDF-star lets you make statements about a triple, which is what edge properties do in an LPG:

@prefix ex: <http://example.org/> .

<< ex:MarieCurie ex:won ex:NobelPrizePhysics >> ex:year 1903 .

3.0.2.3 Relational databases

A knowledge graph can be stored in a relational database, either as a generic triples table or with one table per entity type. Everything is available with standard SQL tooling, but navigating long chains of relationships requires many joins (or recursive queries) and quickly becomes slow and complex.

CREATE TABLE triples (
  subject   TEXT,
  predicate TEXT,
  object    TEXT
);

INSERT INTO triples VALUES
  ('MarieCurie', 'won',    'NobelPrizePhysics'),
  ('MarieCurie', 'bornIn', 'Warsaw');

3.0.2.4 Document stores (JSON)

Document databases such as MongoDB or Couchbase can store entities as nested JSON documents. This is flexible and easy for applications to consume, but relationships are implicit (nested or referenced by ID), so there is no built-in semantics or graph traversal. JSON-LD (see above) is the bridge: it is plain JSON that can be loaded in a document store and still be interpreted as RDF.

3.0.2.5 Virtual knowledge graphs

Instead of copying the data, a virtual knowledge graph (also called Ontology-Based Data Access) keeps the data in its original relational database and exposes it as RDF through mappings such as R2RML, so it can be queried with SPARQL. Tools include Ontop and Morph-KGC. This is useful when the data must stay in its source system.

Approach Model Query language Strength Weakness
RDF triple store Triples SPARQL Standards, interoperability, reasoning Edge properties are awkward (without RDF-star)
Property graph Nodes and edges with properties Cypher, Gremlin, GQL Intuitive, fast traversal No shared vocabulary standard
Relational Tables SQL Mature tooling Costly joins for deep relationships
Document store JSON documents Vendor specific Flexible Implicit relationships
Virtual KG RDF view on existing data SPARQL No data duplication Depends on mapping quality

3.0.3 RDF with OWL or a property graph?

Once you have decided on a graph, the next question is which graph model to use. The two main choices are RDF (optionally with OWL and SHACL) and a labeled property graph such as Neo4j. They overlap a lot, but they are optimised for different goals.

RDF with OWL is the better fit when:

  • the data must be shared or integrated across systems or organisations, since global identifiers (URIs) and shared vocabularies (schema.org, Dublin Core, DCAT, …) make merging graphs straightforward
  • you need inference or consistency checks, e.g. deriving new facts from class hierarchies or detecting contradictions
  • you want to publish linked or open data following W3C standards (SPARQL, SHACL, JSON-LD)

A property graph is the better fit when:

  • the focus is on application-level traversal and analytics, such as shortest paths, recommendations, or network analysis
  • relationships carry many attributes (dates, weights, sources) that you want to store directly on the edge
  • the data stays within a single system, so shared semantics are not a priority
  • your team prefers a developer-friendly query language such as Cypher
RDF + OWL Property graph
Strength Shared semantics, interoperability, reasoning Intuitive modelling, fast traversal
Query language SPARQL Cypher, Gremlin, GQL
Schema Ontology (OWL), shapes (SHACL) Optional, database specific
Edge attributes Via RDF-star or reification Native
Typical use Open data, metadata, data integration Applications, analytics, recommendations

The two are not mutually exclusive. RDF-star brings edge attributes to RDF, and some property graph databases can import and export RDF (for instance, the neosemantics plugin for Neo4j), so you can start with one model and convert later if your needs change.

7.2 Data

In general cases, one piece of information in a relational database will be one identifier, a value in a column, and the column name. In a knowledge graph, this information will be represented as a triple: subject, predicate, object. The subject is the identifier, the predicate is the column name, and the object is the value.

Relation between tables in a relational database will be represented as a triple in a knowledge graph. The subject will be the identifier of the first table, the predicate will be the name of the relation, and the object will be the identifier of the second table.

7.3 Meta-data

7.4 NoSQL and other cases

NoSQL databases and other types of databases may have different structures and representations of data, but the general principle of mapping data to a knowledge graph remains the same. The key is to identify the entities and relationships in the data and represent them as triples in the knowledge graph.

The main difference from a general table in a relational database is that the column name is not necessarily the predicate, and the value is not necessarily the object. The mapping will depend on the specific structure and representation of the data. It is also true for a relational database if the schema is not normalized in the general traditional sense: it is for instance possible to to flatten several tables into one table, where some columns will become elements in a row.

For instance:

Person ID, Type of Data, Value of Data

That can contains:

  • 1, Name, John Doe
  • 1, Age, 30
  • 1, Address, 123 Main St

As such it is closer to a NoSQL database than a relational database (while stored in a relational database, but with a denormalized structure and “losing” some querying capabilities, all queries are still possible but will be more complex and less efficient), and the mapping to a knowledge graph will be different. The subject will be the identifier of the person, the predicate will be the type of data, and the object will be the value of the data.
