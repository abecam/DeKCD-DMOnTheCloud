Building an Assembly

1 What is an assembly?

An assembly in Research Data Management is the connected usage of one or many Research Data Management (RDM) tools to achieve a specific goal. It is a way to combine different tools and resources to create a workflow that meets the needs of a particular research project or task. Assemblies can be simple, involving just a few tools, or complex, involving many tools and resources. It could be with a Research Data Management Platform and other tools like a data repository, a data visualization tool, or a data analysis tool, or between different Research Data Management Platforms, such as a sharing platform, an electronic lab notebook (ELN), and a data repository such as iRODS or Aruna. The goal of an assembly is to streamline the research process, improve data management practices, and facilitate collaboration among researchers.

2 Keep it simple

When working on a Data Management Solution, it is important to think about the actual usage: will the Scientists benefits from it enough that they will use it and justify the cost of building and maintaining it? One benefit might be a requirement of the funding agency, so might be felt by the Scientists as a burden. The role of a Data Management Solution is to reduce the friction as much as possible (together with the training and support from the Data Management Team), so that the benefits, even if not directly felt by the Scientists, will be enough to justify the usage of the Data Management Solution.

As such it is important to keep the assembly as simple as possible, and to avoid adding unnecessary complexity or features that do not directly contribute to the research goals. The assembly should be designed with the end-users in mind, and should be easy to use and understand.

One approach might be to have a specialized Data Management Platform adapted to the specific research domain (such as a Laboratory Notebook for a wet-lab), and to connect it to a central Data Repository. This allows researchers to use the specialized tools they are familiar with, while still ensuring that the data is stored in a secure and accessible location.

In many case, the central Data Repository can be an external service, such as Zenodo, or a managed service provided by the institution, such as iRODS or Aruna. In that case, there might be no need for an assembly, but for connecting the services using APis, and, if possible, to have a single sign-on (SSO) solution for the users. A central SSO is only possible if the Data Management Platform and the Data Repository are both managed by the same institution, or if they are part of a consortium that allows for SSO between institutions.

Another part of an assembly can be a general file storage solution, such as NextCloud, that can be used to store and share files that are not directly related to the research data, but are still important for the research project. One drawback of a general file storage solution is that, by default, the data are unstructured and lack meta-data, so might not be suitable for the main output of the research project. But it can be useful for storing and sharing supplementary materials, such as protocols, presentations, or other documents.

2.1 Small tools

Writting small tools to connect the different parts of the assembly or to provide some additional functionality can be a good approach, as long as the tools are well-documented and maintained. Small tools can be used to automate repetitive tasks, integrate different tools and resources, or provide additional functionality that is not available in the existing tools, such as sending automated emails with some reporting.

Python is a good choice for writing small tools, as it is simple, well documented, widely used in the research community and has a large number of libraries and frameworks that can be used to build tools quickly and easily. Other programming languages, such as R or JavaScript, can also be used to build small tools, depending on the specific needs of the assembly.

In any case, documenting them need to be also for their usage, i.e. that there is a central place where the tools are listed, how to use them, how they work, and where they are used in the assembly. This can be done using a wiki, a documentation website, or other similar tools.

Using a version control system, such as Git, to manage the code and track changes is also important.

We recommend to write this tools following the KISS principle (Keep It Simple, Stupid), so that they are easy to understand and maintain.

3 Avoid using the wrong tools

An important aspect of data management is to use the right tools for the right tasks. Using a tool that is not designed for a specific task can lead to issues with data integrity, security, and usability.

For instance, if there is a need for a general file storage solution, using a dedicated Research Data Management Platform for that purpose might not be the best approach, as it can add unnecessary complexity and noise to the platform. Instead, using a general file storage solution, such as NextCloud, that is designed for that purpose can be a better approach.

The opposite, i.e. using a general file storage solution for storing research data that should be structured and have metadata, is probably a bad idea.

Convoluted ways to connect the data management platforms have the potential to be extremely damaging in the long term. If there is a need for a quick and dirty solution, it is important to ensure that it will be replaced by a proper solution as soon as possible. “Hacks” are generally time bombs and often, if left in place, will be a problem long after anyone properly remember what it does and how it does it. One good way of providing a temporary fix is when it informs by itself of his temporary nature, if possible.

4 Concerns with assemblies

When building an assembly, it is important to consider the following concerns: * Compatibility: Ensure that the tools and resources being used are compatible with each other and can work together seamlessly. * Security: Ensure that the tools and resources being used are secure and protect sensitive data. * Scalability: Ensure that the assembly can handle the volume of data and users that will be involved in the research project.

6 Avoid several logins: central identity management

Authentik, Keycloak, or other identity management systems can be used to provide single sign-on (SSO) capabilities for the assembly. This allows users to log in once and access all the tools and resources in the assembly without having to remember multiple usernames and passwords.

Consortium (such as Life Science login) or institutional identity management systems can also be used to provide SSO capabilities for the assembly. This allows users to log in using their institutional credentials and access all the tools and resources in the assembly without having to remember multiple usernames and passwords.

7 Assemblies between institutions

What is allowed and how to get it allowed?

Tunneling between institutions can be achieved through the use of virtual private networks (VPNs) or other secure communication protocols. This allows researchers from different institutions to access the tools and resources in the assembly as if they were on the same network.

Security and privacy concerns must be addressed when building assemblies between institutions. This may involve implementing access controls, encryption, and other security measures to protect sensitive data.

Performance and reliability concerns must also be addressed when building assemblies between institutions. This may involve optimizing the assembly for performance, implementing redundancy and failover mechanisms, and monitoring the assembly for issues.

8 Using a LLM to build an assembly

8.1 As a general help with online LLMs

Help with APIs, integration, and general assembly building. LLMs can provide guidance on best practices, suggest compatible tools, and help troubleshoot issues that arise during the assembly building process.

Be careful to understand what is being suggested and to verify the information provided by the LLM. LLMs may not always provide accurate or up-to-date information, so it is important to cross-check their suggestions with reliable sources.

8.2 With a local LLM aside the assembly

For instance to help with data analysis, data visualization, or other tasks that are part of the assembly. A local LLM can be used to provide additional support and guidance for researchers working on the assembly. It can for instance help with SparQL queries, data cleaning, or other tasks that require specialized knowledge or expertise.

The simple approach would be using exposed APIs and documentation, without access to the data itself. This allows the LLM to provide guidance and support without compromising the security or privacy of the data being used in the assembly.

The next step would be to provide the LLM with access to the data as read-only (no write operations permitted), allowing it to perform more advanced tasks such as data analysis or visualization. It is still important to ensure that the results of the LLM’s analysis are accurate and reliable, and to verify its suggestions with other sources.

The last step is a “full” approach, where the LLM has full access to the data and can perform any operations necessary to support the assembly. This approach should only be used in cases where the LLM is trusted and has been thoroughly vetted for security and privacy concerns. The access should be limited to the specific tasks required for the assembly, and appropriate safeguards should be in place to protect sensitive data. In no case should the LLM be allowed to make changes to the data without human oversight and approval, and all destructive operation should either be disabled, soft deleted (i.e. not actually deleted but marked as deleted) and/or require human approval before being executed.

8.2.1 Semantic graphs, API documentation and LLMs

Semantic graphs are an useful representation of data, metadata, and their relationships, relying on existing semantic graphs and ontologies to give an unified view. Data represented within a semantic graph that conforms to common semantic graphs and ontologies can be easily integrated with other data sources conforming to the same semantic graphs and ontologies.

The main aspect of a semantic graph is a triple:

(subject, predicate, object)

For instance ("Sample_1", "has_measurement", "Measurement_1")

Links between triples are simply another triple, for instance ("Measurement_1", "is_part_of", "Experiment_1")

But it is often an overkill to use a semantic graph within a Data Management Platform, and most Data Management Platforms rely on a relational database to store their data and metadata.

In that case, the semantic graph can still be built from the relational database. Data will be subject and object, with the column name the predicate. For instance a table with columns sample_id, measurement_id, and temperature will have the following triples: * (sample_id, measurement_id, temperature)

Metadata will be predicate with object (for instance “storage temperature” as predicate and “4°C” as object).

As the schema of the relational database is fixed but not necessarily accessible, the semantic graph can be built from the API documentation, if one is available for the Data Management Platform. The API documentation will describe the endpoints and their parameters, which can be used to construct the triples in the semantic graph.

Most LLMs will know how to build a semantic graph from an API documentation, or if there is another approach better suited. Several tools can also be used to build a semantic graph from an API documentation, or to prepare a semantic graph Query Language endpoint such as SparQL.

One remaining issue is to use existing semantic graphs and ontologies to give an unified view. This is a complex task that requires a deep understanding of the data and its relationships, as well as semantic of existing semantic graphs and ontologies. LLMs can assist in this process by suggesting relevant semantic graphs and ontologies, and helping to map the data to these representations. But there will probably be a need for human expertise to ensure that the mapping is accurate and meaningful.

Note

The data do not have to be stored in a semantic graph, and can rely on the built semantic graph only to be queried using a semantic graph Query Language endpoint such as SparQL.

Note

As the database schema is fixed but the metadata part of the dynamic data, the resulting semantic graph will be a mix of a read-only part (the database schema) and a dynamic part (the metadata). In that case it might be better to create 2 semantic graphs, one for the read-only part and one for the dynamic part. If the data is also stored in a semantic graph, then a 3rd semantic graph can be created to represent the data itself.

8.2.2 Semantic graphs and assemblies

The main benefit of using a semantic graph in an assembly is that it allows for a unified view of the data and metadata across the various tools and resources being used. This also can allow an unique endpoint for querying the data and metadata, regardless of where they are stored or how they are represented.

The building cost will be quite high, and it is not something that can be built by the Scientists themselves, while necessitating a good knowledge of the domain. As such, it can be seen as the last step of building an assembly, and should be considered only if the assembly is expected to be used for a long time and/or by many users.
